## 1. 개요

### 목적
1. 동아리 부원이 만든 코드·작업물을 한곳에 모으고, 다른 부원이 이를 발전시킬 때 **원본과 수정본의 관계를 계보로 남긴다.** (v1.0부터 유지)
2. **[v2.0]** 여러 해에 걸친 동아리의 **조직(회원·직책), 활동(연도·차시), 협업(팀 프로젝트), 결과물(게시판·아카이브)** 을 한곳에 쌓는다.
3. **[v2.0]** 매년 회원이 바뀌어도 대규모 개편 없이 운영할 수 있게 한다.

### 핵심 원칙
1. 학교 Google 계정으로만 가입한다.
2. 수정본은 원본 아래 하위 항목으로 존재하고, 원작자 출처는 자동 표기되며 지울 수 없다.
3. **[v2.0]** 회원은 Google 계정이 아니라 **내부 회원 ID**로 식별한다. 계정이 바뀌어도 이력은 이어진다.
4. **[v2.0]** 기존 데이터와 기록은 삭제·덮어쓰기 하지 않는다. 바꿀 때는 이력을 남긴다.
5. **[v2.0]** 권한은 화면이 아니라 **서버(DB)** 에서 검사한다.

### 대상과 운영 시점 [v2.0]
- 한 동아리 전용 (부원 수십 명)
- 2027년부터 본격 운영. 2027 기준 **12기(2학년), 13기(1학년)**. 이후 매년 새 기수가 들어오고 졸업생이 생긴다.
- 특정 연도·기수에 종속되지 않는 구조로 설계한다.

## 2. 현재 구조 분석 (v1.1 기준) [v2.0]

| 항목 | 현재 |
|---|---|
| 프론트엔드 | 빌드 없는 정적 웹앱 (HTML·CSS·바닐라 JS, 해시 라우터). `js/app.js` 화면, `js/store.js` 데이터 계층(Api), `js/remote.js` Supabase 연결 |
| 백엔드 | 별도 서버 없음. **Supabase**(PostgreSQL + Auth + 자동 REST/RPC) |
| 권한 검사 | 테이블은 RLS로 읽기만 허용, 모든 쓰기는 `security definer` 서버 함수(RPC)에서 검사 |
| 로그인 | Supabase Auth + Google OAuth. 가입 트리거가 학교 도메인·명단을 서버에서 검사 |
| 회원 식별 | `profiles.id` = Supabase 로그인 계정 ID → **Google 계정 = 회원** |
| 권한 | `profiles.role` 한 칸 (member / admin=운영진 / teacher=부장(구 지도교사)), `status` (pending/active/graduated) |
| 파일 저장 | 코드 파일 텍스트를 `versions.files`(JSON)에 저장. 이미지·PDF 등 바이너리는 미지원 |
| 호스팅 | GitHub Pages (`shic0418.github.io/pop-hub`), 서버 DB는 Supabase 무료 요금제(서울) |
| 테스트 | `tests/schema-test.mjs` (PGlite로 권한 규칙 86개 검사), `tests/remote-mock.html` |

### 구현된 기능 (v1.x)
로그인·가입 승인, 코드 프로젝트 업로드·뷰어, 수정본 트리·출처 표기, 버전 기록·비교, 반영 요청, 줄 댓글, 브라우저 실행(Python·HTML), 기수 아카이브(작성자 기수 기준), 내 기여, 알림, 신고·숨김, 관리(가입 승인·부원·설정).

### 현재 구조의 한계
1. **회원 = Google 계정**: 계정을 바꾸면 새 회원이 되어 과거 기록과 끊어진다. (이번 개편의 가장 큰 구조 변경)
2. **직책이 한 칸**: 복수 직책, 서버 관리자, 직책 양도·이력을 표현할 수 없다.
3. **연도·차시 개념 없음**: 기수만 있고 운영 연도·활동 차시가 없다.
4. **바이너리 파일 불가**: 팀 결과물(이미지·영상·PDF 등)을 올릴 수 없다.
5. **협업 단위가 "코드 프로젝트"뿐**: 팀 프로젝트·게시판·공지가 없다.
6. **7일 미사용 시 서버 일시 정지**(아래 10장)와 **백업 부재**.

## 3. 회원·계정 관리 [v2.0]

### 3-1. 내부 회원 ID
- 회원(`profiles`)과 로그인 계정(`user_accounts`)을 **분리**한다.
- 회원에게는 바뀌지 않는 내부 ID(UUID)와 사람이 읽는 회원 번호(`POP-0001` 형식)를 부여한다.
- 게시물·작업물·팀 참여·제작자 정보·직책 이력·연도별 기록은 모두 **회원 ID**에 연결된다.
- 한 회원에 Google 계정 여러 개를 연결할 수 있다. 로그인은 어느 연결 계정으로 해도 같은 회원이 된다.

### 3-2. 계정 변경·연결 흐름
| 상황 | 처리 |
|---|---|
| 신규 가입 | 학교 도메인 확인 → 새 회원 + 계정 연결 생성 (명단에 있으면 바로 활동, 아니면 승인 대기) |
| 새 학년에 계정이 바뀜 (사전 등록) | 관리자가 연도 명단에 "기존 회원 POP-0012의 새 이메일"로 등록 → 그 계정으로 첫 로그인 시 **기존 회원에 자동 연결** |
| 새 계정으로 먼저 로그인함 | 승인 대기 회원으로 들어옴 → 관리자가 "기존 회원에 연결(병합)" 실행 → 계정이 기존 회원으로 옮겨지고 빈 대기 회원은 정리 |
| 쓰지 않는 계정 | 관리자가 연결 해제 (마지막 계정은 해제 불가) |

- **이름이 같다는 이유로 자동 병합하지 않는다.** 병합은 관리자 승인으로만 한다.
- 모든 연결·해제·병합은 감사 기록에 남는다.

### 3-3. 연도별 회원 명단
- `membership_history`에 **연도별로 독립 저장**: 기수, 그 해 학년, 그 해 직책, 활동 기간, 상태.
- 다음 해에 학년·직책이 바뀌어도 과거 연도 기록은 그대로 남는다.
- 관리자는 CSV(이름·기수·학년·이메일·회원번호·직책)로 새 연도 명단을 일괄 등록할 수 있다. 등록 전에 기존 회원/신규/중복 여부를 미리 보여 준다. (2단계)

### 3-4. 졸업
- 회원 상태를 "졸업생"으로 바꾼다. 계정·작업물·제작자 표기·연도별 기록은 그대로 유지되고, 본인 기록은 계속 열람할 수 있다.

## 4. 권한 체계 [v2.0]

### 4-1. 직책 (복수 보유 가능)
| 코드 | 직책 | 성격 |
|---|---|---|
| `owner` | 최고 관리자(창립 관리자) | 관리자 권한 + 관리자 임명·해임, 최고 관리자 이양 |
| `admin` | 관리자 | 전체 운영 (기존 "지도교사/부장" 권한이 여기로 옮겨옴) |
| `president` | 부장 | 동아리 활동·프로젝트·게시판·공지 운영 |
| `vice` | 차장 | 부장 보조, 부장과 비슷한 운영 기능 |
| `server` | 서버 관리자 | 서버·DB 상태 확인, 연결 점검, 백업 상태 확인 |
| (없음) | 부원 | 기본 회원 |

- 한 회원이 여러 직책을 동시에 가질 수 있고(예: 관리자+부장+서버 관리자), 권한은 **합산**한다.
- 직책과 무관하게 막아야 하는 작업(데이터 영구 삭제, 관리자 변경, 복구)은 **별도 규칙**으로 관리자 이상만 허용한다.

### 4-2. 권한별 기능표

`*` 서버 관리자의 세부 권한(상세 상태·백업 상태·오류 기록 열람)은 관리자가 켜고 끌 수 있다. 회원 개인정보(이메일 등)와 관리자 기능은 **어떤 설정으로도** 서버 관리자에게 주어지지 않는다.

- 부장·차장에게 추가로 허용할 기능(예: 계정 연결 처리)도 관리자가 **위임 설정**으로 켤 수 있다. 위임 가능한 기능은 미리 정한 목록 안에서만 고를 수 있다.

### 4-3. 직책 임명·양도
1. 관리자가 직책과 새 보유자를 고른다.
2. 화면에 기존 보유자를 보여 준다.
3. 최종 확인("기존 부장 A는 일반 부원이 됩니다").
4. 새 보유자에게 직책 부여 → 기존 보유자의 그 직책만 해제 (계정·기록은 그대로).
5. 이력을 감사 기록에 남기고, 당사자들에게 알림.
- 한 사람이 부장과 차장을 함께 맡는 것도 허용한다.
- 부장·차장은 "한 명만" 두는 것이 기본(양도 방식)이고, 관리자·서버 관리자는 여러 명 가능.

### 4-4. 관리자 승계와 안전장치
- **관리자는 여러 명** 둘 수 있다. 최고 관리자는 관리자 권한을 차기 운영진에게 주고도 **자신의 권한을 유지**한다.
- **최고 관리자 이양은 2단계**: 현 최고 관리자가 이양을 제안 → 받는 사람이 본인 계정으로 로그인해 **수락**해야 완료. 수락 전에는 취소 가능.
- **관리자 0명 방지**: 마지막 관리자(최고 관리자 포함)의 해임·졸업 처리는 서버가 거부한다.
- **계정 분실 대비**: 관리자는 Google 계정을 2개 이상 연결해 둘 것을 권장. 모두 잃었다면 다른 관리자가 새 계정을 연결해 준다.
- **최후 복구 절차**: 관리자 전원이 접근 불가하면, Supabase 프로젝트 소유자(GitHub 계정)가 SQL 편집기에서 `select private.emergency_grant_owner('POP-0001')`를 실행한다. 이 함수는 웹에서 호출할 수 없다.
- 모든 직책 변경·이양은 감사 기록(관리자만 열람)에 남는다.

## 5. 운영 연도와 차시 [v2.0]

### 5-1. 운영 연도
- 운영 연도 N = **N년 3월 1일 ~ N+1년 2월 말일**, 한국 시간(Asia/Seoul) 기준.
- `academic_years`에 연도별 1행. 현재 연도 외에는 **읽기 전용**(관리자는 수정 가능, 수정 이력 기록).

### 5-2. 자동 연도 전환
- 서버 함수 `ensure_academic_year()`가 "오늘(서울 시간) 기준 운영 연도"를 계산해 없으면 만들고 1~10차시를 만든다.
- **멱등**: 몇 번 실행해도 같은 연도·차시가 중복 생성되지 않는다(고유 제약 + `on conflict do nothing`).
- 실행 시점: ① 매일 새벽 서버 예약 작업(pg_cron) ② 앱 접속 시 ③ 관리자 수동 실행. 어느 쪽이 먼저 실행돼도 결과는 같다.
- 전환 시 처리: 이전 연도를 "보관" 상태로 표시(데이터는 그대로), 새 연도 생성, 1~10차시 생성, 전년도 활동 회원을 새 연도 명단 후보로 복사(관리자가 확정).
- 기존 작업물의 연도는 **업로드 날짜로 계산 가능하므로** 자동으로 정한다. **차시는 추정하지 않는다** — 차시 미분류 목록을 관리자에게 보여 준다.

### 5-3. 차시
- 연도마다 기본 10차시. 차시별 제목·날짜·설명을 운영진이 입력.
- 차시 페이지: 그 차시에 연결된 개인 작업물·팀 프로젝트 결과물을 카드/목록으로 보여 준다. 차시 내 검색·제작자 필터.
- 결과물은 **한 번만 저장**하고 여러 차시가 참조한다(연결 테이블).

## 6. 팀 프로젝트 [v2.0, 2단계]

### 6-1. 생성과 구성
- 이름, 설명, 목표, 팀장, 팀원(초대→수락), 관련 연도·차시(여러 개), 대표 이미지, 상태.
- 상태: 기획 중 → 진행 중 → 제출 대기 → 완료 → 게시 완료 → 보관.

### 6-2. 작업 공간
- 팀원 목록, 설명·목표, 공지·메모, 토론(댓글), 진행 상황, 결과물 목록.
- **파일 업로드와 버전 관리**: 같은 파일을 다시 올리면 새 버전으로 쌓인다(덮어쓰기 없음). 버전마다 업로더·날짜·메모 기록.
- 기본 흐름: 생성 → 초대 → 각자 외부 도구(Claude 등)로 작업 → 업로드 → 검토 → 새 버전 → 최종본 확정 → 팀장 제출 → 게시.
- 파일은 **Supabase Storage**(비공개 버킷)에 저장하고, DB에는 경로·크기·종류만 기록. 팀원·운영진만 열람, 게시된 최종본만 전체 부원 열람.

### 6-3. 공동 제작자 표시
1. 팀장이 최종 제작자 명단(이름 표기·역할)을 작성
2. 각 팀원이 본인 등록·표기를 **확인 또는 거절**
3. 필요 시 수정 → 전원 확인되면 확정
4. 확정 명단을 결과물에 연결해 게시 시 "제작자: 홍길동, 김철수…"로 표시
- 게시 후 관리자가 정당한 사유로 수정할 수 있으며 이력이 남는다.
- 안내 문구: "제작자 표시는 기여 기록이며, 법적 저작권 귀속을 자동으로 결정하지 않습니다. 공개 범위와 권리에 대해 팀원과 합의하세요."

## 7. 게시판 [v2.0, 2단계]

- 탭: **전체 / 동아리 / 자유** (+ 공지는 상단 고정)
- 동아리 게시물: 차시 결과물·팀 프로젝트·공동 제작물·행사 기록. 연도·차시·프로젝트와 연결.
- 자유 게시물: 개인 창작물. 동아리 공식 결과물과 **색·배지로 구분**.
- 작성: 제목, 내용(마크다운), 대표 이미지, 첨부, 유형, 태그, 공개 범위(부원 전체 / 운영진만). 팀 프로젝트 결과물이면 제작자 명단 자동 연결.
- 댓글, 반응(좋아요), 검색(제목·태그·작성자·연도·차시), 최신/인기 정렬, 수정·삭제(소프트 삭제), 신고, 운영진 관리.
- 기존 "코드 프로젝트"(수정본 트리)는 그대로 유지하고, 게시물에서 코드 프로젝트를 연결할 수 있다.
- **비로그인 외부 공개는 하지 않는다**(개인정보 보호). 필요하면 추후 "외부 공개" 옵션을 별도 검토.

## 10. 서버 휴면 문제와 서버 관리 [v2.0]

### 10-1. 원인
- 웹페이지(GitHub Pages)는 잠들지 않는다.
- **Supabase 무료 요금제는 7일 동안 요청이 없으면 프로젝트를 "일시 정지(Paused)"** 한다. 데이터는 지워지지 않으며, 대시보드에서 Restore하면 그대로 돌아온다.
- 즉 "초기화"가 아니라 "정지"다. 정지된 동안은 앱이 서버에 연결할 수 없다.
- 정지된 프로젝트는 **웹 앱의 버튼으로 깨울 수 없다**(깨우려면 비밀 관리 토큰이 필요하고, 이를 웹페이지에 넣으면 보안 사고가 된다).

### 10-2. 해결책
1. **예방 – 정기 연결 확인**: GitHub Actions 예약 작업이 **3일에 한 번** 가벼운 상태 확인 함수(`ping`)를 호출한다. 실제 DB 조회 1회이며 결과를 상태 기록에 남긴다. 과도한 반복 요청은 하지 않는다.
   - 참고: 무료 요금제의 휴면 정책을 우회하는 용도로 해석될 여지가 있다. 장기 운영이 확실해지면 **Pro 요금제(월 $25, 정지 없음·일일 백업)** 를 권장한다.
2. **상태 페이지**: 누구나 "연결 확인"으로 서버·DB 응답 여부와 마지막 정상 시각을 본다. 서버 관리자·관리자는 DB 크기, 테이블별 행 수, 저장 공간 사용량, 최근 백업, 최근 오류를 본다.
3. **정지되었을 때**: 앱이 연결 실패를 감지하면 "서버가 일시 정지되었을 수 있습니다. 서버 관리자에게 알려 주세요"와 복구 방법(대시보드 Restore)을 안내한다.
4. **"깨우기"와 "초기화"는 완전히 분리**: 연결 확인·깨우기는 읽기 전용이며 데이터를 바꾸지 않는다. 데이터 삭제·복원은 관리자 전용, 최종 확인 + 대상 이름 재입력을 요구한다.

### 10-3. 백업
- GitHub Actions가 **주 1회** DB를 내보내고(`pg_dump`), **암호화**(비밀 문구는 GitHub Secrets)한 뒤 비공개 아티팩트로 90일 보관. 결과를 상태 기록에 남긴다.
- DB 연결 문자열·암호는 GitHub Secrets에만 두고 웹페이지에는 절대 넣지 않는다.
- 업로드 파일(Storage)도 같은 작업에서 목록·내용을 내려받아 함께 보관(2단계, 파일 기능 도입 후).
- 복원은 관리자가 절차서에 따라 수행(자동 복원 버튼은 두지 않는다 — 잘못 누르면 되돌릴 수 없으므로).

## 11. 데이터베이스 설계 [v2.0]

기존 테이블은 **삭제하지 않고** 확장한다. ★ = 신규

| 테이블 | 역할 | 비고 |
|---|---|---|
| `profiles` | 회원 (내부 ID, 회원 번호 ★`member_no`, 이름, 기수, 상태) | 로그인 계정과의 강제 연결(FK) 제거 → 계정이 사라져도 회원은 남음. `role` 칸은 호환용으로만 유지 |
| ★`user_accounts` | 로그인 계정 ↔ 회원 연결 (여러 개 가능) | 이메일, 연결 일시, 연결한 사람, 상태 |
| `member_emails` | 회원 대표 이메일 (본인·운영진만 열람) | 유지 |
| ★`roles` | 직책 종류 (owner/admin/president/vice/server) | 표시 이름·순서 |
| ★`user_roles` | 회원별 복수 직책 | (회원, 직책) 고유 |
| ★`role_permissions` | 직책별 위임·세부 권한 켜기/끄기 | 위임 가능 목록 안에서만 |
| ★`owner_transfers` | 최고 관리자 이양 제안·수락 | 2단계 승인 |
| ★`audit_logs` | 직책·계정·설정·삭제 등 주요 변경 이력 | 관리자만 열람, 수정·삭제 불가 |
| ★`academic_years` | 운영 연도 (시작·종료일, 상태) | 연도 고유 |
| ★`sessions` | 연도별 차시 (1~10) | (연도, 번호) 고유 |
| ★`membership_history` | 연도별 회원 기록 (기수·학년·직책 스냅샷) | (회원, 연도) 고유 |
| ★`project_sessions` | 코드 프로젝트 ↔ 차시 연결 | 결과물은 한 번만 저장 |
| `projects` | 코드 프로젝트 (+ ★`year` 운영 연도) | 기존 유지 |
| `versions` … `reports` | 기존 기능 | 유지 |
| ★`system_status` | 연결 확인·백업·오류 기록 | 과도한 기록 방지(간격 제한) |
| ★`team_projects`, `team_members`, `team_files`, `team_file_versions`, `team_credits`, `team_messages`, `team_project_sessions` | 팀 프로젝트 | 2단계 |
| ★`posts`, `post_files`, `post_sessions`, `post_comments`, `post_reactions` | 게시판·공지 | 2단계 |

- 모든 주요 데이터는 UUID 고유 ID. 참조 관계는 외래 키로 유지. 자주 찾는 칸에 인덱스.
- 모든 쓰기는 서버 함수에서 권한을 다시 검사하고, 중요한 변경은 `audit_logs`에 남긴다.
- 파일 바이너리는 DB가 아니라 Storage에 두고, 파일 접근은 Storage 정책으로 다시 검사한다.

### 기존 데이터 이전(마이그레이션)
1. 실서버에서 **백업 스키마로 전체 복사** 후 시작
2. 기존 `profiles.id`(=로그인 계정 ID)를 그대로 회원 ID로 쓰고, 같은 값으로 `user_accounts` 1행씩 생성 → 기존 참조 전부 그대로 유효
3. 기존 직책 변환: `teacher`(현 "부장" 표시) → **최고 관리자 + 관리자**, `admin`(운영진) → **차장**
4. 기존 코드 프로젝트의 운영 연도 = 업로드 날짜 기준 자동 계산(2026 운영 연도). 차시는 미분류로 둔다
5. 이전 후 행 수·참조 무결성 검증 쿼리를 실행하고 결과를 기록

## 14. 보안·운영 원칙 [v2.0]
- 화면에서 버튼을 숨기는 것은 보호가 아니다. **모든 권한은 서버 함수와 RLS에서 검사**한다.
- 다른 회원의 계정 정보는 본인·관리자만 수정한다.
- 비공개 팀 파일은 팀원·운영진만 열람(Storage 정책).
- 업로드는 허용 확장자·크기를 서버에서 검사, 실행 파일 차단, 사용자 코드는 격리 환경에서만 실행(기존 유지).
- 되돌릴 수 없는 작업은 최종 확인 + 대상 이름 재입력.
- 비밀 정보(DB 암호, 관리 토큰, 백업 비밀 문구)는 GitHub Secrets·Supabase에만 둔다. 웹페이지에는 공개 키(anon)만.

## 15. 예상 문제와 대응
| 문제 | 대응 |
|---|---|
| 회원·계정 분리 중 기존 참조가 끊김 | 기존 회원 ID를 그대로 유지하는 방식으로 이전, 이전 전 백업·이전 후 검증 |
